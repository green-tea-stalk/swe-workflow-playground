# 要件定義書: 掲示板アプリケーション（Bulletin Board Application）

## 1. 背景と動機（Context & Motivation）

### 1.1 課題の説明（Problem Statement）
ソフトウェアエンジニアリング作業を自動化する `swe-workflow` プラグインの機能および品質を総合的に評価・検証するためのテストベッドアプリケーションが必要です。このテストベッドは、仕様策定、DbC（Design by Contract: 契約による設計）、自動テスト実行、ならびにJava/Micronaut、MySQL、Angularを用いたモダンなコンポーネント実装を網羅する、エンドツーエンドのフルスタックソフトウェア開発ワークフローを実証できる構成でなければなりません。

### 1.2 ビジネスおよび技術目標（Business & Technical Goals）
- メッセージの投稿および既存投稿の逆時系列（降順）閲覧が可能な、信頼性が高く実用的な掲示板システム（BBS: Bulletin Board System）を提供する。
- 自動化されたプラグイン作業、スタック検証、および厳格なSDD（Spec-Driven Development: 仕様駆動開発）プロセスを検証するための堅牢なリファレンス実装を提供する。
- コンテナ化されたMySQLデータベース、Micronaut Data JDBCバックエンド、およびAngular Materialフロントエンドの間でクリーンなアーキテクチャ分離を保証する。

### 1.3 対象ペルソナおよびステークホルダー（Target Personas & Stakeholders）
- **プラグイン評価者（開発者 / テスター）**: 自動タスクのトリガー、コード品質の検証、テストスイートの実行、およびWebブラウザを通じた掲示板の操作により、プラグインの能力を評価する。
- **掲示板利用者（エンドユーザー）**: 認証の手間なく匿名でWebインターフェースにアクセスし、過去のメッセージの閲覧や新規メッセージの投稿を行う。

## 2. 利用シナリオおよびユースケース（User Scenarios & Use Cases）

### 2.1 ユースケース1: ページネーションによるメッセージ一覧閲覧
- **アクター**: 掲示板利用者 / プラグイン評価者
- **前提条件**: アプリケーションバックエンドおよびMySQLデータベースが稼働中であり、通信可能であること。
- **トリガー**: 利用者がWebアプリケーションにアクセスする、またはページ操作を行う。
- **基本フロー**:
  1. 利用者が掲示板のトップページにアクセスする。
  2. フロントエンドが `/api/messages?page=0&size=50` へHTTP GETリクエストを送信する。
  3. バックエンドが投稿日時の降順（`createdAt DESC`）でソートされた指定ページのメッセージを取得する。
  4. バックエンドがページネーションメタデータ（`page`, `size`, `totalElements`, `totalPages`）を算出する。
  5. バックエンドがHTTPステータス `200 OK` とともにページネーションペイロードを返却する。
  6. フロントエンドが画面上部からメッセージを描画し、ページネーション操作UI（現在のページ番号、次へ/前へボタンなど）を表示する。
- **代替フロー**:
  - *初期（空）状態*: データベース内にメッセージが1件も存在しない場合、バックエンドは `totalElements: 0` の空リストを返却し、フロントエンドはメッセージが存在しない旨を案内するメッセージを表示する。
  - *ページ移動*: 利用者がページネーション操作UIで別のページ番号を選択した場合、フロントエンドはそのページ番号のデータを要求し、一覧を再描画する。
- **例外フロー**:
  - *サーバー / ネットワーク障害*: バックエンドまたはデータベースに接続できない場合、バックエンドまたはネットワーク層がエラーを返却し、フロントエンドは明確なエラーバナーを表示する。
- **事後条件**: 要求されたページのメッセージ一覧が、投稿日時の降順で利用者に表示されていること。

### 2.2 ユースケース2: 新規メッセージの投稿
- **アクター**: 掲示板利用者 / プラグイン評価者
- **前提条件**: 掲示板のトップページが読み込まれ、ビューポート最下部に固定された入力フォームが表示されていること。
- **トリガー**: 利用者が入力欄に必要な情報を入力し、「投稿（Submit）」ボタンをクリックする。
- **基本フロー**:
  1. 利用者が画面下部に固定されたフォームに、名前、任意のメールアドレス、タイトル、およびメッセージ本文を入力する。
  2. 利用者が「投稿」ボタンをクリックする。
  3. フロントエンドが各入力欄の妥当性をローカルで検証する。
  4. フロントエンドがペイロード `{ name, email, title, message }` を伴って `/api/messages` へHTTP POSTリクエストを送信する。
  5. バックエンドがすべてのフィールド制約（文字数上限、必須・非空白チェック、メールアドレス形式）を検証する。
  6. バックエンドがサーバー側の現在時刻（`createdAt`）を付与し、新規メッセージをMySQLデータベースに永続化して、HTTPステータス `201 Created` とともに保存されたメッセージを返却する。
  7. フロントエンドが入力フォームのすべての入力欄をクリアする。
  8. フロントエンドがメッセージ一覧の先頭ページ（`page=0`）を再取得し、新規投稿されたメッセージを最上部に表示する。
- **代替フロー**:
  - *メールアドレス省略*: 利用者がメールアドレス欄を空欄のまま投稿した場合、システムは `email` をnullとして処理し、投稿されたメッセージの表示時にもメールアドレスリンクを表示しない。
- **例外フロー**:
  - *クライアント側バリデーション失敗*: 送信前にいずれかの入力項目が制約に違反している場合、フロントエンドは送信ボタンを無効化するか、入力欄付近にエラーメッセージを表示して送信を中止する。
  - *サーバー側バリデーション失敗*: 不正なペイロードがバックエンドに到達した場合、バックエンドは構造化されたエラー詳細を含むHTTPステータス `400 Bad Request` で拒絶し、フロントエンドは入力内容を保持したまま不備のある入力欄を明示する。
  - *サーバー / データベース障害*: データベースへの永続化に失敗した場合、バックエンドはHTTPステータス `500 Internal Server Error` を返却し、フロントエンドはフォームの入力内容を保持したままエラー通知を表示する。
- **事後条件**: 新規メッセージがMySQLに確実に永続化され、メッセージ一覧の最上部に表示されること。

## 3. ビジュアルモデリング（Visual Modeling）

```mermaid
sequenceDiagram
    autonumber
    actor User as 掲示板利用者 / 評価者
    participant UI as Angular フロントエンド
    participant API as Micronaut バックエンド
    participant DB as MySQL データベース

    %% メッセージ閲覧フロー
    User->>UI: アプリケーションを開く
    activate UI
    UI->>API: GET /api/messages?page=0&size=50

    API->>DB: SELECT * FROM messages ORDER BY created_at DESC LIMIT 50 OFFSET 0
    activate DB
    DB-->>API: 取得結果レコードおよび総件数
    deactivate DB
    API-->>UI: 200 OK { content: [...], totalElements, totalPages, page, size }
    deactivate API
    UI-->>User: メッセージ一覧（上部）と固定入力フォーム（下部）を描画
    deactivate UI

    %% メッセージ投稿フロー
    User->>UI: 名前、メール、タイトル、メッセージを入力して投稿をクリック
    activate UI
    UI->>UI: フォーム入力値を検証
    alt バリデーション失敗
        UI-->>User: 入力不備のエラーメッセージを表示
    else バリデーション成功
        UI->>API: POST /api/messages { name, email, title, message }
        activate API
        API->>API: 制約チェック（Bean Validation）
        alt 不正なペイロード
            API-->>UI: 400 Bad Request { errors: [...] }
            deactivate API
            UI-->>User: バリデーションエラーを表示
        else 妥当なペイロード
            API->>DB: INSERT INTO messages (...) VALUES (...)
            activate DB
            DB-->>API: 保存成功（自動採番ID、作成日時）
            deactivate DB
            API-->>UI: 201 Created { id, name, email, title, message, createdAt }
            deactivate API
            UI->>UI: 入力フォームをクリア
            UI->>API: GET /api/messages?page=0&size=50 (一覧再取得)
            activate API
            API->>DB: 最新メッセージ一覧を取得
            activate DB
            DB-->>API: 最新メッセージデータ
            deactivate DB
            API-->>UI: 200 OK (更新後の一覧)
            deactivate API
            UI-->>User: 最上部に新規投稿が反映された一覧を再描画
        end
    end
    deactivate UI
```

## 4. 機能要件（Functional Requirements）

すべての機能要件は、標準EARS構文パターンおよびRFC 2119 / RFC 8174の大文字キーワード（日本語標準対応表現）を用いて定義されています。

| 要件ID | EARSパターン種別 | 仕様記述文（RFC 2119 / 8174 準拠） | 検証方法 |
| :--- | :--- | :--- | :--- |
| **REQ-001** | 遍在的（Ubiquitous） | システムは、メインの掲示板画面において、ビューポート最下部に常時固定表示されるメッセージ投稿フォーム（Sticky Footer）を表示しなければならない（MUST）。 | 自動E2Eテスト / UI検査 |
| **REQ-002** | 遍在的（Ubiquitous） | システムは、固定入力フォームの上部スクロール可能領域において、掲示板メッセージを作成日時の降順（`createdAt DESC`）で表示しなければならない（MUST）。 | 自動統合テスト |
| **REQ-003** | イベント駆動（Event-driven） | 利用者がメッセージ一覧を要求したとき、またはページ移動を行ったとき、システムはデフォルトで1ページあたり厳密に50件（0開始のページインデックス使用）のページネーションを適用してメッセージを取得・返却しなければならず（MUST）、`page`, `size`, `totalElements`, `totalPages` を含むページネーションメタデータを付与しなければならない（MUST）。 | 自動統合テスト |
| **REQ-004** | イベント駆動（Event-driven） | 利用者が非空白の名前（1〜50文字）、任意のメールアドレス（0〜100文字、入力時はRFC準拠形式）、非空白のタイトル（1〜100文字）、および非空白のメッセージ本文（1〜1,000文字）を含む有効なメッセージを送信したとき、システムはサーバー側で生成した作成日時とともにメッセージをデータベースに記録し、HTTPステータス `201 Created` を返却しなければならない（MUST）。 | 自動統合テスト |
| **REQ-005** | イベント駆動（Event-driven） | メッセージが正常に送信・保存されたとき、システムは固定下部フォームのすべての入力項目をクリアし、先頭ページの最上部に新規投稿メッセージが反映されるよう一覧を再取得しなければならない（MUST）。 | 自動E2Eテスト / 統合テスト |
| **REQ-006** | 望ましくない挙動（Unwanted Behavior） | 利用者が必須項目の欠落（名前、タイトル、メッセージ本文が空白のみ）または最大長の上限超過（名前 > 50文字、メールアドレス > 100文字、タイトル > 100文字、本文 > 1,000文字）を含むメッセージを送信しようとした場合、システムは送信を拒絶し、項目別のバリデーションエラーを伴うHTTPステータス `400 Bad Request` を返却しなければならず（MUST）、レコードをデータベースに永続化してはならない（MUST NOT）。 | 自動単体 / 統合テスト |
| **REQ-007** | 望ましくない挙動（Unwanted Behavior） | 利用者が標準的なメールアドレス形式（RFC 5322）に準拠しないメールアドレスを入力して送信した場合、システムは送信を拒絶し、HTTPステータス `400 Bad Request` を返却しなければならず（MUST）、レコードをデータベースに永続化してはならない（MUST NOT）。 | 自動単体 / 統合テスト |
| **REQ-008** | オプション機能（Optional Feature） | メッセージレコードに空でないメールアドレスが含まれる場合、システムはメッセージカード内で投稿者名と並んでメールアドレスを表示しなければならず（MUST）、メールアドレスがnullまたは省略されている場合、システムは空文字の遺物等を表示することなく投稿者名のみを表示しなければならない（MUST）。 | 自動UIコンポーネントテスト |
| **REQ-009** | 望ましくない挙動（Unwanted Behavior） | メッセージの取得中または永続化中にデータベース接続エラーや予期せぬ実行時障害が発生した場合、システムはHTTPステータス `500 Internal Server Error` を返却し、内部エラー詳細を安全にログ記録しなければならず（MUST）、クライアントに対して内部スタックトレースやデータベース接続認証情報を漏洩してはならない（MUST NOT）。 | 自動フォールト注入テスト |

## 5. 非機能要件（Non-Functional Requirements）

- **NFR-PERF-001 (性能)**: バックエンドAPIは、標準的なローカル開発環境において、メッセージ一覧取得および作成要求を500ミリ秒以内に処理し応答しなければならない（MUST）。
- **NFR-SEC-001 (セキュリティ & 入力無害化)**: システムは、XSS（Cross-Site Scripting: クロスサイトスクリプティング）を防止するためにDOMへのレンダリング前に利用者が入力したすべてのテキストを無害化またはエスケープしなければならず（MUST）、SQLインジェクションのリスクを排除するためにMicronaut Data JDBC経由のパラメータ化クエリを使用しなければならない（MUST）。
- **NFR-COMP-001 (実行基盤 & 依存関係ベースライン)**: システムは、Java 21 LTS、MySQL 8.4 LTS、Micronaut Framework 4.x、およびAngular最新安定版（Angular Materialを含む）で動作しなければならない（MUST）。
- **NFR-REL-001 (トランザクション & 信頼性)**: システムは、メッセージ作成を単一のアトミックなデータベーストランザクション内で管理し、永続化処理の途中でエラーが発生した場合は安全に停止（Fail-Closed）しなければならない（MUST）。
- **NFR-DEV-001 (コンテナ化 & ローカル環境構築)**: システムは、設定済み認証情報および永続化ボリュームを備えたローカルMySQLデータベースを1コマンドで初期化できる `docker-compose.yml` ファイルを提供しなければならない（MUST）。

## 6. スコープ外（Out of Scope）

以下の機能および要件は、本仕様の対象外として明示的に除外されます：
- ユーザー認証および認可機能（ユーザーアカウント、パスワード、ログインセッション、ロールベースのアクセス制御は導入しない）。
- メッセージの編集および削除操作。
- ファイルやマルチメディアの添付機能（テキストのみの投稿）。
- スレッド返信構造（ツリー状の返信や引用返信は導入しない）。
- ソーシャルインタラクション（いいね、高評価/低評価、絵文字リアクションは導入しない）。
